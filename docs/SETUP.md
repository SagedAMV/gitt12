# تحديث 0.2.1
المشروع المخصص أُنشئ ونُشرت الهجرات والوظائف بالفعل؛ لا تعِد إنشاء الجداول. راجع CURRENT_DEPLOYMENT.md. سكربت النشر وتهيئة المشرف يرفضان أي مشروع غير المشروع الجديد. الإرشادات العامة أدناه مرجع للتهيئة والصيانة.

# إعداد بيئة تطوير فعلية

## 1. اختيار مشروع Supabase
أنشئ أو اختر مشروعاً مخصصاً للتطبيق. لا تستخدم مشروعاً لتطبيق مختلف دون مراجعة. أثناء العمل ظهر مشروع متصل باسم `unihub1`، لكنه لم يُعدّل ولم تُقرأ مفاتيحه.

## 2. إعداد GitHub App
- حساب GitHub شخصي واحد مخصص للتطبيق.
- صلاحية Repository Contents: Read and Write، وMetadata: Read.
- تثبيت التطبيق على حساب المالك واعتماد الوصول إلى مستودعاته المطلوبة.
- لا حاجة لصلاحية حذف المستودع؛ التطبيق يزيل الربط من قاعدة البيانات فقط.
- احفظ App ID وInstallation ID واسم المالك ومفتاح App الخاص على الخادم فقط.
- المكتبة تتطلب مفتاح RSA بصيغة PKCS#8 PEM. عند تنزيل مفتاح PKCS#1، حوّله محلياً:

```bash
openssl pkcs8 -topk8 -nocrypt -in github-app.private-key.pem -out github-app.pkcs8.pem
```

لا ترفع أياً من الملفين إلى Git.

## 3. الهجرات والوظائف
ثبّت Supabase CLI، وسجّل الدخول محلياً. على بيئة تطوير:

```bash
export SUPABASE_PROJECT_REF='<project-ref>'
bash scripts/deploy.sh
```

البرنامج يطلب تأكيد اسم المشروع قبل تطبيق الهجرات ونشر الوظائف. `verify_jwt=false` على بوابة الوظائف مقصود: الوظائف المحمية تتحقق من Bearer token عبر `auth.getUser` بنفسها، وحالة الحساب والصلاحيات من قاعدة البيانات؛ لا يعني تعطيل التفويض.

## 4. الأسرار
استخدم ملفاً خاصاً خارج المستودع أو واجهة Supabase Secrets، وفق `supabase/.env.example`:
- `GITHUB_APP_ID`
- `GITHUB_INSTALLATION_ID`
- `GITHUB_OWNER`
- `GITHUB_PRIVATE_KEY` (PKCS#8، يمكن استخدام أسطر فعلية أو `\n`)
- `RATE_LIMIT_SECRET` (قيمة عشوائية طويلة، لا تستخدم مثالاً ثابتاً)

`SUPABASE_URL` و`SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY` متوفرة عادةً ضمن بيئة Edge Functions المستضافة؛ تحقق من مشروعك. لا ترسل service-role للتطبيق أو للواجهة.

لا تضبط `VAULT_TEST` في بيئة التشغيل؛ هو لتعطيل بدء خادم Deno داخل اختبارات الوحدة فقط.

## 5. Auth
- فعّل Email Auth للدخول الداخلي بالبريد الاصطناعي.
- عطّل التسجيل المباشر للمستخدمين من إعدادات Auth؛ وظيفة registration تستخدم Admin API فقط.
- جميع الهويات التي ينشئها الخادم تستخدم `email_confirm=true` دون إرسال رسائل.
- لا يوجد استرجاع بريد حقيقي؛ إعادة التعيين بواسطة المشرف.
- فعّل تدوير refresh tokens، وراجع مدة JWT وسياسات Supabase Auth لمشروعك.
- امنع الوصول العام إلى endpoint bootstrap (لا يوجد مثل هذا endpoint في الكود).

## 6. إنشاء المشرف الأول
من جهازك الآمن، وفّر متغيرات البيئة محلياً دون حفظها في Git:

```bash
export SUPABASE_URL='https://<project-ref>.supabase.co'
# أدخل SUPABASE_SERVICE_ROLE_KEY بطريقة آمنة في بيئة الطرفية؛ لا تشاركه في المحادثة.
python3 scripts/bootstrap-admin.py
```

يطلب السكربت تأكيد المشروع وكلمة المرور مرتين باستخدام getpass. اسم المشرف `sagedkhan746`. قيد قاعدة البيانات يمنع مشرفاً ثانياً ويمنع تسمية المشرف بغير الاسم المعتمد. إذا فشل إدراج الملف الشخصي بعد إنشاء هوية Auth يحاول السكربت التراجع بحذف الهوية.

## 7. تفعيل التطبيق
- أدخل Project URL والمفتاح العام من شاشة الدخول أو عبر local.properties ثم البناء.
- ادخل بالمشرف، ثم الإدارة ← ربط مستودع.
- أنشئ مستخدماً أو وافق على طلب، ثم امنحه صلاحية المستودع.
- اختبر بحساب USER طلب وظائف إدارية مباشرة وتأكد من رفضها.

## 8. قبل الإنتاج — إلزامي
- تجربة على أجهزة Android فعلية: SAF، استمرار/إلغاء WorkManager، قتل العملية، فقد الشبكة، فتح الملفات، صلاحيات FileProvider.
- اختبارات تكامل حقيقية مع Supabase وGitHub لمختلف حالات الحسابات.
- اختبار رفع/تنزيل وحمل ضمن ميزانية Edge Functions. لا ترفع الحد إلى 90 MB بمجرد تعديل ثابت.
- تنزيل ZIP مع فصل الشبكة ونفاد القرص وفحص CRC والمسارات.
- فحص سياسة المعدل خلف بوابة Supabase؛ `x-forwarded-for` يُفترض أنه مضبوط من البوابة. لا تعرض الوظائف مباشرة خلف وكيل يثق بقيمة يرسلها العميل.
- وضع سياسة احتفاظ لسجل النشاط، وتشغيل `prune_rate_limits()` دورياً بصلاحية خادمية.
- نسخ احتياطي لقاعدة البيانات والأسرار، ومراقبة الأخطاء وحدود GitHub API.
- مفتاح توقيع إصدار وحماية نسخ المفتاح ومتطلبات المتجر الحالية.
